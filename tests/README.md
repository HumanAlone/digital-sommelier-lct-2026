# Проверка текущего функционала

Запуск из корня проекта. Нужны Python и Node.js 22. Docker не требуется.

```powershell
python -m pip install -r requirements-ci.txt
python -m pytest -q
node --test tests/frontend/*.test.mjs
```

Если Windows запрещает запуск дочернего процесса тестового раннера:

```powershell
node --test --experimental-test-isolation=none tests/frontend/*.test.mjs
```

## Что проверяется

- Python: HTTP-контракт FastAPI, разные форматы изображений, преобразование в RGB, отсутствие файла, повреждённый файл, отсутствие распознавания, ошибка пайплайна и последующий успешный запрос, CORS, неизвестные маршруты.
- Каталог: уникальность идентификаторов, согласованность CSV/JSON/индексов и наличие локальных фотографий.
- Инфраструктура: наличие скачанных ML-артефактов, Unix-переносы строк скриптов. Для этих проверок предварительно нужен `git lfs pull`; CI скачивает LFS-файлы автоматически.
- Frontend: поиск, сочетание фильтров, пагинация, избранное и восстановление после перезагрузки, история, сравнение, подборки, дневник, экранирование пользовательских заметок, гостевой профиль, подбор сомелье, запрет камеры и освобождение запоздавшего видеопотока, успешное и неуспешное сканирование.
- API-клиент: локальный кэш каталога, относительные URL фотографий, multipart-загрузка, ошибки сети/HTTP, сохранение и удаление токена, истёкшая сессия, неполные ответы авторизации.

## Границы проверок

Frontend-тесты выполняют настоящий JavaScript приложения в изолированном Node VM. DOM, камера, хранилище и сеть заменены управляемыми тестовыми объектами. Это функциональные тесты логики и обработчиков, а не полноценные браузерные E2E: они не проверяют CSS, реальное разрешение камеры, клики по отрисованному DOM и особенности мобильных браузеров.

API-тесты используют реальный FastAPI TestClient, но заменяют тяжёлый ML-пайплайн. Они не измеряют качество распознавания и не доказывают совместимость весов с установленной версией Transformers. Проверки клиентской авторизации не означают, что серверная авторизация уже реализована.

Ручные сценарии для камеры, контейнеров и настоящей модели: `docs/TEST_CASES.md`. Для проверки реального распознавания нужны рабочий Docker, все модели и размеченные фотографии.
